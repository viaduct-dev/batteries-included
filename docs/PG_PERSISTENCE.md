# PG Persistence setup

Batteries Included uses the published pg-persistence plugin and runtime. The plugin discovers
persistent Node types and generates the database model and pg_graphql metadata. The runtime handles
GraphQL requests, variables, errors, record decoding and node references.

The application supplies its Viaduct schema, migrations, HTTP client, endpoint, request headers,
resolvers and authorization rules. It does not contain a separate GraphQL transport or PostgREST
database client.

## Configuration

`backend/gradle.properties` pins both library versions. The build resolves the plugin and packaged
runtime from Maven Central's snapshot repository. No `mavenLocal()` or persistence source checkout
is needed.

`appModule` configures `DbClient` with `SUPABASE_URL/graphql/v1`. Every resolver request supplies
the user's bearer token and `SUPABASE_ANON_KEY`. Never use the service-role key for application
requests. `SupabaseService` continues to use the Auth API for sign-in, sign-up, token refresh and
verification.

`AuthenticatedSupabaseClient` contains a few application operations used outside node resolvers:
membership checks, inserts preserving the existing direct-object mutation responses, membership
removal by its unique group/user pair, and user administration functions. These delegate encoding,
decoding and transport to the library. The SQL JSON wrappers exist because pg_graphql does not
expose anonymous TABLE return types or void mutation results; `executeJson` decodes those results.

## Existing database upgrade

Back up production before applying the two `20260915` migrations through the existing migration
process. Do not reset a deployed database.

- UUID primary-key columns become `_uuid_id`; their values do not change.
- New generated `id` columns contain Viaduct global IDs.
- Existing foreign keys, cascading deletes, indexes, RLS policies and group ownership are retained.
- The owner-membership trigger and owner check are updated for the renamed column.
- `owner_id` defaults to `auth.uid()`, so the public create input needs no owner field.
- The group schema uses `DateTime` for timestamps and `ID` for UUID fields.
- Membership `id` and its typed `groupId` now return opaque Viaduct global IDs. User IDs remain
  Supabase UUID strings.
- New SQL-function wrappers retain the existing admin checks. The old destructive test cleanup
  function is no longer executable by ordinary application users.

The migrations include the reviewed SQL generated by pg-persistence. Future changes should use
`./gradlew buildViaductEffectiveModel` and review the resulting files, not copy the old DDL.
Database-only defaults, Auth foreign keys and authorization policies remain application-owned.

Local Supabase now uses PostgreSQL 17 and must provide pg_graphql SQL-function support.
Upgrade older local PostgreSQL installations using a backed-up migration workflow; changing
`major_version` is not an in-place database upgrade. Existing hosted projects likewise need a
compatible pg_graphql version before deploying this backend.

## Authorization and errors

Viaduct's group checker remains enabled. Database RLS is retained as an additional safeguard.
Owners can add members; owners or the member themselves can remove a membership.
Removing zero rows returns `false`, not an unconditional success.

pg_graphql errors throw through the library and reach the Viaduct response's `errors` array.
A group hidden by RLS returns null from the nullable `group` query. Node lookup follows Viaduct's
node-resolver error behavior. Database-backed list relationships return node references; the
corresponding node resolver fetches the selected fields.

The `groups` query follows the library's database cursors. For plain node-list relationships
such as `Group.members`, pg-persistence follows those cursors automatically; no membership field
resolver is needed. These APIs load all accessible rows. Prefer a paginated connection for new,
potentially large collections so callers can request a bounded page.

## Verification

```bash
cd backend
./gradlew test
```

Tests start the project's local Supabase instance. The new integration tests execute actual
Viaduct GraphQL operations with the production checker factory, authenticated users, and pg_graphql.
They cover inserts, typed references, nested membership reads, node lookup, pagination, duplicate
rows, denied writes, removal, search and admin mutations.

To test alongside another Supabase project, prepare a separate Supabase work directory with a
unique `project_id`, non-conflicting ports, and a `supabase/migrations` symlink to this checkout's
`schema/migrations`. Set `SUPABASE_WORKDIR`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` and
`SUPABASE_SERVICE_ROLE_KEY` before running tests. Only test fixture creation uses the service-role
key; resolver operations use each authenticated user's token.
